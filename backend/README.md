# qwork backend

API qwork на Java 21. Для локальной сборки нужны JDK 21 или новее и Maven. PostgreSQL используется при заданном `QWORK_DATABASE_URL`. Без него API открывает локальную SQLite по `QWORK_DB` или стандартному пути в `backend/data`.

Запуск из корня проекта для телефонов в одной локальной сети:

```sh
mvn -f backend/pom.xml package
QWORK_HOST=0.0.0.0 java -jar backend/target/qwork-api.jar
```

Для запуска с локальными серверными настройками используйте `backend/run-local.sh`:

```sh
cp backend/.env.example backend/.env.local
chmod 600 backend/.env.local
mvn -f backend/pom.xml package
./backend/run-local.sh --check
./backend/run-local.sh
```

Заполните `backend/.env.local` перед запуском. Файл исключён из Git. Скрипт читает значения буквально, без выполнения команд и подстановки переменных; для значения с пробелами можно использовать внешние одинарные или двойные кавычки. Поддерживается формат `KEY=value`, комментарии задаются отдельной строкой с `#`. Значения из файла заменяют одноимённые переменные окружения. Для другого файла настроек задайте `QWORK_ENV_FILE`.

Скрипт сохраняет прежнюю SQLite в `backend/data/qwork.sqlite3` независимо от текущей папки терминала и по умолчанию слушает `0.0.0.0:8787`. Он запускает готовый JAR и не останавливает уже работающий сервер: если порт занят, завершите прежний запуск в его терминале. `--check` проверяет наличие сборки и полноту настроек, не показывает секреты, не открывает сервер и не отправляет письма.

Проверка готовности API и базы доступна на `/health`. Expo использует прежние маршруты и форматы ответов. Для локального запуска на другом порту задайте `QWORK_PORT`.

Сервер сохраняет загруженные JPEG и PNG размером до 12 МиБ и разрешением до 16 мегапикселей в исходном виде. Запрос `GET /tasks/{taskId}/photos/{photoId}?original=1` отдаёт оригинал с его типом содержимого, включая ранее сохранённые WebP. Для просмотра в приложении используется отдельная JPEG-копия с водяным знаком для фотоотчётов.

## PostgreSQL и перенос SQLite

Для управляемой PostgreSQL передайте строку подключения `QWORK_DATABASE_URL` в окружение API. Для собственной PostgreSQL в Compose задайте `QWORK_POSTGRES_PASSWORD` (например, случайную шестнадцатеричную строку) и добавьте файл `compose.postgres.yaml`:

```sh
docker compose -f compose.yaml -f compose.postgres.yaml up -d --build
```

Оба способа применяют миграции при запуске. Встроенная PostgreSQL доступна только внутри Compose, данные лежат в томе `postgres_data`.

Для переноса существующих данных остановите запись в старую базу, сделайте согласованную резервную копию SQLite и запустите импорт из корня проекта с заданным `QWORK_DATABASE_URL`:

```sh
java -cp backend/target/qwork-api.jar qwork.ImportSqlite /path/to/qwork-backup.sqlite3
```

Импорт переносит компании, пользователей, активные сессии, приглашения, заявки и историю с прежними идентификаторами. Целевая PostgreSQL должна быть пустой. Проверьте вход и список заявок до переключения клиентов и сохраните резервную копию SQLite для отката. Не открывайте порт PostgreSQL в интернет.

В `mobile/.env.local` укажите адрес API, доступный с телефона, и перезапустите Expo. В приложении зарегистрируйте компанию и создайте сотрудника. На втором телефоне откройте его персональное приглашение и войдите с его логином и паролем. Создайте заявку на первом телефоне и назначьте её этому сотруднику. После отправки отчёта руководитель открывает заявку со статусом «На проверке» и принимает работу или возвращает её на доработку с причиной.

Роль руководителя объединяет назначение заявок, проверку отчётов, планирование, аналитику и разбор конфликтов. Миграция переводит прежних диспетчеров в роль `manager` с сохранением аккаунтов и сеансов. Создатель компании управляет приглашениями, подразделениями и временными паролями. Решения по отчётам доступны по заявкам своей компании. Сервер сохраняет фактического автора решения в истории.

Новую командировку сотрудник подаёт на себя через `POST /trip-offers`. Создатель компании назначает трёх разных руководителей через `POST /trip-approval-settings`. Состав согласующих фиксируется при подаче. `POST /trip-offers/{id}/approval` принимает решения по порядку. Поездка появляется после третьего согласования. Импорт Excel в кабинете сотрудника создаёт его черновики. Ранее выданные назначения рассматриваются по прежним правилам.

## Резервное копирование PostgreSQL

Из папки `backend` выполните команды в том же окружении Compose, в котором запущена база. Если при запуске заданы `COMPOSE_FILE` или `COMPOSE_PROJECT_NAME`, используйте их и здесь. Каталог резервных копий держите вне репозитория.

```sh
umask 077
mkdir -p "$HOME/qwork-backups"
backup="$HOME/qwork-backups/qwork-$(date -u +%Y%m%dT%H%M%SZ).dump"
./postgres-backup.sh backup "$backup"
./postgres-backup.sh restore "$backup" qwork_restore_check
```

Скрипт публикует файл только после успешного `pg_dump` и проверки архива. Восстановление выполняется в одной транзакции в новой базе с именем, начинающимся с `qwork_restore_`. После восстановления проверьте данные в новой базе, прежде чем переключать на неё API. После пробной проверки можно удалить эту отдельную базу или при следующей проверке выбрать другое имя.

Для управляемой базы, например Neon, используйте прямой адрес подключения без пула и PostgreSQL CLI той же или более новой основной версии. Задайте параметры подключения в окружении:

```sh
export QWORK_BACKUP_MODE=direct
export PGHOST='<прямой хост из Neon Connect>'
export PGPORT=5432 PGDATABASE=neondb PGUSER='<роль PostgreSQL>'
export PGSSLMODE=verify-full PGSSLROOTCERT=system
export PGPASSFILE="$HOME/.pgpass"
```

Подставьте имя базы и роль из Neon Connect. Запишите пароль в файл `PGPASSFILE` с правами 600 в формате `хост:порт:*:роль:пароль`. Для `PGSSLROOTCERT=system` нужны клиенты PostgreSQL 17 или новее. После настройки выполните те же команды `backup` и `restore`. Для пробного восстановления выберите параметры отдельной ветки или проекта Neon и роль с правом создания базы. Храните архивы в защищённом хранилище отдельно от сервера и регулярно проверяйте восстановление.

## Публичный запуск

Для тестового стенда на Render и Neon есть [render.yaml](../render.yaml). В панели Render можно также создать Web Service вручную: среда Docker, корневая папка `backend`, контекст сборки `.`, Dockerfile `./Dockerfile`, проверка готовности `/health`. Команду запуска возьмёт из Dockerfile.

Задайте `QWORK_DATABASE_URL` из Neon Connect в секретах Render. Для Java с проверкой сертификата и имени сервера добавьте к параметрам строки `sslmode=verify-full` и `sslfactory=org.postgresql.ssl.DefaultJavaSSLFactory`. В сборке с поддержкой Render задайте `QWORK_TRUST_PROXY=render` для ограничения попыток входа по адресу клиента, который передаёт Cloudflare на стороне Render. Для писем используйте публичный адрес сервиса, а ключ почтового API задавайте отдельно в Render.

Для API и приглашений в настройках приложения укажите один выданный Render адрес `https://…onrender.com`. Бесплатный сервис засыпает после простоя. Первый запрос после пробуждения может занять около минуты.

На VPS с Docker Compose направьте DNS-запись вашего домена на сервер и откройте входящие порты 80 и 443. Скопируйте исходники из папки `backend`. Для нового развёртывания используйте пустой том базы. Существующую базу переносите отдельной резервной копией SQLite.

Из папки `backend` запустите стек, подставив свой домен:

```sh
QWORK_DOMAIN=qwork.example.com docker compose up -d --build
curl --fail https://qwork.example.com/health
```

Caddy получает сертификат и перенаправляет HTTP на HTTPS. Порт Java API доступен внутри сети Compose. Локальная SQLite сохраняется в томе `qwork_data`, встроенная PostgreSQL — в томе `postgres_data`. Команда `docker compose down -v` удаляет тома.

Задайте в настройках сборки мобильного приложения адрес API и адрес приглашений:

```dotenv
EXPO_PUBLIC_QWORK_API_URL=https://qwork.example.com
EXPO_PUBLIC_QWORK_INVITE_URL=https://qwork.example.com
```

Раздайте сотрудникам установочную сборку qwork с этими настройками. Персональное приглашение откроет страницу с кнопкой запуска приложения. Сотрудник также может вставить ссылку на экране входа. Токен после символа `#` не входит в HTTP-запрос к странице.

## Срочные push-уведомления

Бэкенд записывает доставку вместе с событием и отправляет её через Expo Push Service после сохранения. Срочный уход получают руководители компании, аварийное назначение получает выбранный сотрудник. Приложение регистрирует устройство после входа. Выход из аккаунта и отзыв сессии удаляют привязку устройства.

Если в настройках проекта Expo включена защита отправки, добавьте серверную переменную `QWORK_EXPO_PUSH_ACCESS_TOKEN` с ключом отправки. Храните ключ в окружении бэкенда.

## Дополнительная почта и автоматические пароли

При создании сотрудника логин обязателен, а поле `email` можно оставить пустым. Если `password` не передан, сервер генерирует временный пароль и возвращает его в `temporaryPassword` вместе с приглашением. Так же работает сброс пароля сотрудника. После активации сотрудник входит по логину и личному паролю.

В профиле можно добавить или изменить почту с подтверждением текущего пароля. Подтверждённая почта становится дополнительным идентификатором входа. Основной логин сохраняется. До подтверждения почта не даёт дополнительного доступа и не используется для восстановления пароля.

Для писем можно использовать Brevo или Resend. Провайдер и настройки задаются в окружении Java API:

- `QWORK_EMAIL_PROVIDER` — `brevo` или `resend`. Новый пример настроек использует Brevo; если переменная отсутствует, сохраняется прежний выбор Resend.
- `QWORK_EMAIL_API_KEY` — ключ API почтового сервиса, хранить только на сервере.
- `QWORK_EMAIL_FROM` — разрешённый сервисом адрес отправителя. Для Brevo укажите только почтовый адрес, подтверждённый в настройках отправителей; имя qwork добавляет сервер. Для Resend используйте разрешённого вашим аккаунтом отправителя.
- `QWORK_PUBLIC_URL` — публичный HTTPS-адрес этого Java API, без завершающего пути.

Для нового подключения через Brevo:

1. Создайте аккаунт на [странице регистрации Brevo](https://app.brevo.com/account/register).
2. Добавьте адрес отправителя и подтвердите его по письму сервиса.
3. Создайте API v3 key и сохраните его только в `backend/.env.local`.
4. Укажите `QWORK_EMAIL_PROVIDER=brevo`, подтверждённый адрес в `QWORK_EMAIL_FROM` и публичный адрес Java API в `QWORK_PUBLIC_URL`.
5. Выполните `./backend/run-local.sh --check`, затем запустите API через `./backend/run-local.sh`.
6. В профиле qwork нажмите «Отправить подтверждение». После успешной отправки откройте полученное письмо и подтвердите адрес.

Для локального запуска задайте все три значения в `backend/.env.local` и запустите API через `./backend/run-local.sh`. Для писем нужен разрешённый почтовым сервисом отправитель; наличие API-ключа само по себе не подтверждает возможность отправки на любой адрес. `QWORK_PUBLIC_URL` должен вести на этот Java API и открываться с устройства получателя: адрес `localhost` или локальный Wi-Fi-адрес не подходит для публичных ссылок. Если используется временный HTTPS-адрес, при его смене обновите настройку и запросите новое письмо.

Эти настройки относятся только к Java API. API-ключ и строку подключения к базе не добавляйте в `mobile/.env.local`, `EXPO_PUBLIC_*` или код приложения. Сохранение адреса почты в профиле не отправляет письмо автоматически: пользователь отдельно нажимает «Отправить подтверждение».

### Временная HTTPS-ссылка только для писем

Для локальной проверки без покупки домена можно запустить отдельный почтовый шлюз из корня проекта:

```sh
QWORK_PORT=8787 QWORK_MAIL_GATEWAY_PORT=8788 java -cp backend/target/qwork-api.jar qwork.MailPublicGateway
```

Шлюз слушает только `127.0.0.1:8788`. Он разрешает страницы `/verify-email`, `/reset-password`, скрипт `/auth-mail.js` и два действия с одноразовым токеном: `/auth/email/verify` и `/auth/password/reset`. Маршруты входа, регистрации, отправки писем, пользователей и заявок через шлюз недоступны.

Если Cloudflare Tunnel установлен, направьте временный туннель именно на этот шлюз:

```sh
cloudflared tunnel --url http://127.0.0.1:8788 --no-autoupdate --protocol http2
```

Полученный HTTPS-адрес сохраните в `QWORK_PUBLIC_URL`, после чего перезапустите Java API через `./backend/run-local.sh`. Основной адрес приложения `EXPO_PUBLIC_QWORK_API_URL` для этого менять не требуется. Перед отправкой настоящего письма проверьте, что публичная страница `/verify-email` открывается, а `/tasks` отвечает 404.

Временная ссылка работает, пока включён компьютер и запущены API, шлюз и туннель. После перезапуска туннеля адрес может измениться: обновите `QWORK_PUBLIC_URL`, перезапустите API и запросите новое письмо. Для постоянного использования нужен стабильный публичный адрес.

Эти переменные передаются API и через Compose. Письма подтверждения и восстановления ведут на страницы `/verify-email#…` и `/reset-password#…`. Ссылка действует один час. Подтверждение выполняется по нажатию кнопки. Токен не возвращается в API-ответе и не передаётся в URL запроса страницы. После смены пароля открытые сеансы завершаются.

Если отправка не настроена, API явно отвечает об отсутствии почтового сервиса. Вход по логину и выдача нового временного пароля создателем компании доступны. Для локальных автоматических проверок можно направить `QWORK_EMAIL_API_URL` на имитатор по HTTP на loopback-адресе. В обычном запуске применяется HTTPS API выбранного сервиса.

### TMS Report в Telegram

Бот запускается отдельным процессом. По команде `/start` инженер видит назначенные ему объекты или возвращается к черновику. Он выбирает объект, отправляет одно видео после обслуживания СКУД, затем описывает результат. К отчёту можно приложить фото и документы. После подтверждения бот копирует материалы в закрытый чат проверки, добавляет карточку с объектом, инженером, результатом и временем отправки и подтверждает доставку инженеру. Черновики и состояние доставки хранятся в базе, файлы — в Telegram. Инженер может отменить черновик через `/cancel`.

В личном чате кнопка **«Меню»** рядом с полем ввода показывает команды по роли пользователя. Инженеру доступны добавление отчёта и отмена черновика, руководителю — список несданных отчётов и настройка срока. Если роль изменилась, команда `/start` обновит меню.

1. Зарегистрируйте бота через [BotFather](https://t.me/BotFather) командой `/newbot` и добавьте его в закрытую группу, где руководители будут проверять отчёты. Разрешите боту отправлять сообщения и медиа.
2. Из каталога `backend` соберите JAR, подготовьте конфигурацию и прочитайте токен без вывода на экран.

   ```sh
   mvn package
   mkdir -p data
   cp telegram-reports.example.json data/telegram-reports.json
   read -rs QWORK_TELEGRAM_BOT_TOKEN
   export QWORK_TELEGRAM_BOT_TOKEN
   ```

3. Перед первым запуском отправьте боту `/id` в личных чатах инженеров, а в группе — `/id@имя_бота`, подставив имя бота из BotFather. Запустите команду ниже при остановленном боте и внесите показанные ID и список объектов в `data/telegram-reports.json`. В `assignments` укажите для каждого Telegram ID массив ID его объектов из `sites`. При наличии `assignments` инженер без записи получает пустой список. Старые конфигурации без `assignments` показывают весь каталог настроенным инженерам. После запуска бот отвечает на `/id` в личном чате.

   ```sh
   java -cp target/qwork-api.jar qwork.TelegramReports --ids
   ```

4. Запустите бота.

   ```sh
   java -cp target/qwork-api.jar qwork.TelegramReports
   ```

Пути можно задать через `QWORK_TELEGRAM_CONFIG` и `QWORK_TELEGRAM_DB`. После изменения конфигурации перезапустите процесс.

#### Проверка отчётов

В `reviewers` укажите Telegram ID и имена руководителей. Каждый руководитель может узнать свой ID командой `/id` в личном чате бота. В закрытой группе у новых отчётов появятся кнопки **«Принять»** и **«На доработку»**. Для возврата руководитель отвечает на сообщение бота с запросом замечания. Инженер получает замечание в личном чате, может исправить результат и сохранить материалы либо отправить обновлённые материалы. При повторной отправке номер отчёта сохраняется.

Если `reviewers` пуст или отсутствует, бот доставляет отчёты в группу для архива. Отчёты, отправленные до включения проверки, остаются в истории в исходном виде.

#### Сроки сдачи отчётов

Руководитель задаёт срок в личном чате с ботом командой `/deadline ДД.ММ.ГГГГ ЧЧ:ММ`. Время указывается по часовому поясу Казахстана. Без дополнительных параметров срок применяется ко всем назначенным парам «сотрудник — объект». После времени можно добавить Telegram ID сотрудника, а за ним код одного объекта из каталога.

Команда `/missing` показывает руководителю ожидаемые и просроченные отчёты по объектам. Команда `/missing 2` открывает вторую страницу. Отчёт снимается со списка после отправки сотрудником, до проверки руководителем. Отчёты предыдущего периода и доработки по ним сохраняются в истории. Повтор команды с тем же сроком сохраняет состояние сдачи.

По истечении срока бот отправляет сотруднику одно напоминание со списком объектов, по которым отчёты ещё ждут. Сотрудник должен предварительно открыть личный чат и нажать Start. На Render Free бот проверяет просрочки при пробуждении. Во время сна сервиса напоминание ждёт следующего запуска.

#### Круглосуточный запуск на Linux-сервере

Нужны доступ по SSH, Docker с Compose и постоянный диск. Бот сам забирает сообщения у Telegram по HTTPS. Достаточно исходящего доступа в интернет.

1. Перенесите код проекта на сервер. На Mac остановите бота перед переносом данных. Перенесите по SSH три файла из `backend/data` в закрытый каталог на сервере. Это `.telegram-token`, `telegram-reports.json` и `telegram-reports.sqlite3`. Для SQLite можно снять консистентную копию командой `.backup` утилиты `sqlite3`. Держите токен и рабочие данные вне Git.
2. На сервере из корня проекта подготовьте каталог данных и запустите контейнер. Вместо `/secure/staging` укажите каталог с перенесёнными файлами.

   ```sh
   sudo install -d -m 700 -o 10001 -g 10001 backend/data/telegram
   sudo install -m 600 -o 10001 -g 10001 \
     /secure/staging/.telegram-token \
     /secure/staging/telegram-reports.json \
     /secure/staging/telegram-reports.sqlite3 backend/data/telegram/
   docker compose -f backend/compose.telegram.yaml up -d --build
   docker compose -f backend/compose.telegram.yaml logs --tail 50 telegram
   ```

3. С выключенным локальным процессом проверьте `/start` и отправьте тестовый отчёт в согласованную закрытую группу. Для одного токена держите запущенным один экземпляр бота. Храните резервные копии базы и каталога отдельно от диска сервера и проверяйте восстановление на копии.

#### Бесплатный стенд Render и Neon

Создайте отдельный Render Web Service с тарифом Free. В настройках выберите Docker, путь `./backend/Dockerfile`, контекст `./backend` и путь проверки `/health`. В поле Docker Command укажите `java -cp /app/qwork-api.jar qwork.TelegramReportWebhook`. Оставьте доступ к рабочему API qwork на его текущем сервисе.

В разделе Environment задайте переменные для отдельной базы и бота.

| Переменная | Значение |
| --- | --- |
| `QWORK_TELEGRAM_DATABASE_URL` | Строка подключения к PostgreSQL выделенного проекта Neon с TLS |
| `QWORK_TELEGRAM_BOT_TOKEN` | Действующий токен BotFather |
| `QWORK_TELEGRAM_WEBHOOK_SECRET` | Отдельная случайная строка из латинских букв, цифр, `_` и `-` |
| `QWORK_TELEGRAM_CONFIG_JSON` | Содержимое каталога бота в виде JSON одной строкой |

Вместо `QWORK_TELEGRAM_CONFIG_JSON` можно загрузить каталог как Secret File `telegram-reports.json` и задать `QWORK_TELEGRAM_CONFIG=/etc/secrets/telegram-reports.json`. Секреты и рабочий каталог храните вне Git.

Перед переключением проверьте `/health` публичного сервиса. Остановите локального бота, сделайте копию SQLite командой `.backup` и перенесите её в пустую базу PostgreSQL. Команда запускается из `backend` с `QWORK_TELEGRAM_DATABASE_URL` в окружении.

```sh
java -cp target/qwork-api.jar qwork.TelegramReportMigration /secure/telegram-reports.sqlite3
```

Зарегистрируйте в Telegram Bot API webhook по адресу `https://<имя-сервиса>.onrender.com/telegram/webhook`. Передайте `secret_token` из `QWORK_TELEGRAM_WEBHOOK_SECRET`, `max_connections=1`, `allowed_updates=["message","callback_query"]` и `drop_pending_updates=false`. Дождитесь подтверждения через `getWebhookInfo`. Проверьте `/start` в личном чате, затем отправку и приёмку нового отчёта. Для возврата к локальному опросу удалите webhook через `deleteWebhook` с `drop_pending_updates=false` и восстановите актуальное состояние до запуска локальной копии.

Render Free засыпает после простоя. Первый запрос после сна может задержаться примерно на минуту. Приём сообщений и черновики хранятся в PostgreSQL, поэтому локальный диск Render для них не используется.
